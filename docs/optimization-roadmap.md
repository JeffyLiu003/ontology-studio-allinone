# 下一阶段优化建议

以下按业务 AI Coding 的可用性排序。覆盖诊断与快照差异已经实现，仍保留后续深化方向。

| 优先级 | 方向 | 建议交付 | 对用户的价值 |
|---|---|---|---|
| 已交付 / 待深化 | 建模质量与覆盖透明度 | 按语言/框架展示支持与未支持项；标记只有模块而缺少实体/接口的结果；可定位的解析失败清单；补充通用 Java/JPA/Spring 解析与误映射回归样例 | 先判断图谱是否可用，避免把“生成成功”误认为业务覆盖完整 |
| 部分交付 | 快照差异 / 后续增量分析 | 节点/字段/规则/流程/接口变更对比，按受影响范围重新分析 | 看清代码更新后的业务变化，减少重复评审 |
| P1 | 编码上下文包 | 按需求与选中节点导出相关模型、源码锚点、规则、待确认事项、建议测试范围及版本清单 | 可以直接交给编码 Agent，减少整仓库模型上下文 |
| P1 | 代码图谱双向关联 | 用仓库版本、文件路径、符号与证据哈希连接业务模型和代码图谱，支持双向跳转 | 将业务影响落实到实现，避免只看业务图或只看调用链 |
| P1 | 领域评审基线 | 区分源码反推、业务确认、新需求目标规格；新快照只对可核对的未变更模型提出继承建议 | 让确认过的业务知识逐步形成可复用开发约束 |
| P2 | 任务与存储管理 | 任务分页、按项目与状态筛选、磁盘占用、保留策略预览、批量清理及备份恢复 | 工程数量增多后仍能高效管理 |
| P2 | Agent 工具接入 | 本地 Skill 工作流与只读 MCP 查询，固定 project/snapshot，记录引用证据 | 让编码过程中按需读取业务知识，并能追溯实际使用的模型 |

建议先做建模质量与覆盖透明度，再做快照差异和编码上下文包。现有通用适配器主要做静态模式识别，扩展图谱动画不能替代语义准确性提升。

已交付：覆盖与质量页面、扫描清单、候选匹配与缺口定位、新旧快照字段/关系/证据比较及差异导出。尚未交付：全面 Java AST、增量解析、自动合并评审。任务 3 的范围与决策见 [编码上下文包方案](coding-context-proposal.md)。
